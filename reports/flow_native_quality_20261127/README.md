## 記憶體與交接

11/26 有 **16 次私人記憶體超限、17 次 FLOW 退出／重新啟動，其中 3 次為 0xC0000005**。3 次均在同一程序記憶體警報後約 14–17 秒退出。程序重開不代表記憶體成長已修好；3 次退出碼也不足以識別原生故障模組。

本次確認並修正以下程式缺陷：

1. **行情結構中的原生 BSTR 沒有釋放。** 隨附 SDK 的型別庫確認 SKSTOCKLONG 有 4 個 BSTR，兩個查價介面的結構參數均為 `[in,out]`。comtypes 的 BSTR 位於 ctypes Structure 內時，結構被回收不會代替呼叫端釋放 SDK 寫入的字串。現在每次查價先複製數值與文字至 Python，再於 `finally` 釋放原生字串並清空指標；同位址結構別名不重複釋放，錯誤回碼／例外亦清理。
2. **COM 釋放順序錯誤。** 原券商執行緒在 Reply／Order／Center 的介面與事件訂閱仍被保留時呼叫 CoUninitialize。現在同一 STA 先退出行情監控、解除事件訂閱、釋放介面及事件循環，再關閉 COM。
3. **清理失敗仍釋放物件／程序提前退出。** LeaveMonitor 或 Unadvise 失敗時，保留仍有效的物件、事件接收器與 owner 鎖；原執行緒不再使用 daemon。正常關閉會自動繼續等待／重試清理，期間禁止新工作，不進行另一次登入或任何金融動作。沒有強殺、移除活鎖或清除防重送帳本。
4. **事件泵的回呼生命週期不安全。** comtypes 1.4.17 PumpEvents 每次分別建立註冊及移除用的控制台回呼。在保留回呼以檢查指標的隔離實驗中，移除用指標不同、移除失敗；已用原指標成功清理。這是回呼契約缺陷的重現，**不是 11/26 崩潰的堆疊重現**。正式券商路徑改為 Windows 原生訊息派送及 CoWait，不再逐次註冊控制台回呼；測試確認隱藏視窗訊息仍在原 STA 被派送。
5. 閒置派送不再複製整份金融回報歷史，短等待也不再固定擴張成 250ms。金融回報與正式帳本保留完整。
6. **Windows 虛擬環境的 PID 追蹤錯誤。** Python 3.14 隔離測試重現 Popen.pid 為轉接程序、心跳 PID 為實際 Python，導致守護一直等待心跳／量錯程序。現在直接啟動原 Python 並沿用 CPython 的虛擬環境啟動契約，保留原隔離套件。真正虛擬環境子程序測試確認 PID、套件及環境都正確，原實際程序心跳 → 自動驗收 → 人工停止測試也已通過。這是此次額外發現的啟動缺陷，沒有證據將它追認為 11/26 三次崩潰的來源。契約依據為 [CPython Windows venv 啟動器](https://github.com/python/cpython/blob/main/PC/venvlauncher.c)。

依據：[Microsoft BSTR 所有權](https://learn.microsoft.com/en-us/cpp/atl-mfc-shared/allocating-and-releasing-memory-for-a-bstr?view=msvc-170)、[COM 記憶體規則](https://learn.microsoft.com/en-us/windows/win32/com/memory-management-rules)、[CoUninitialize](https://learn.microsoft.com/en-us/windows/win32/api/combaseapi/nf-combaseapi-couninitialize)、[控制台回呼](https://learn.microsoft.com/en-us/windows/console/setconsolectrlhandler)、[CoWait](https://learn.microsoft.com/en-us/windows/win32/api/combaseapi/nf-combaseapi-cowaitformultiplehandles)。SDK 型別庫雜湊與欄位契約見 sdk_contract.json。
