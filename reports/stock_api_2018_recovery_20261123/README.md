# 證券 API 2018 狀態查詢與恢復

使用者要求處理 `2018` 的 fallback，確認是否為誤觸或官方缺失，維持不交易期貨及選擇權，並推送修正與實機檢查結果。

## 查明的原因與判定邊界

群益官方錯誤碼表及隨附 V2.13.59 文件指出，`2018` 除了尚未簽署、帳戶條件之外，也可能是無法取得簽署狀態，例如 TLS／網路問題。僅憑錯誤碼名稱不能斷定未簽署，更不能判定程式正在使用期貨。先前將它直接解讀為必須補簽的結論過於確定。

本機 Internet TLS 設定值為 10240（0x2800），包含 TLS 1.2；SCHANNEL 的 TLS 1.2 Client 沒有明確停用設定。這只能確認設定，不能證明 SDK 對同意書服務的實際請求一定成功。本次沒有修改登錄檔或 TLS 設定。

原程式的確存在恢復缺口：Center 登入已成功，後續 `ConnectByID` 回傳 `2018` 時，工作執行緒丟棄該會話，再基於避免重複登入的規則永久阻止重試。於是暫時狀態查詢失敗也只能重啟整個程序。這是本次修正的本地問題。尚無證據可以將當時的上游 `2018` 歸因為券商程式缺陷或期貨誤觸。

原健康檢查每分鐘顯示的 `2018` 來自被快取的同一次連線失敗，沒有重新呼叫券商確認，不能把那些時間戳解讀為券商持續回傳新錯誤。

官方 `ConnectByID` 文件定義非零值為失敗，因此本次不會忽略 `2018`、改用舊帳務解封交易，或切換模擬／期貨市場。

## 恢復流程

1. 在原有會話呼叫 `ConnectByID`，保存實際回傳碼。
2. 僅遇到 `2018` 時，以原 Center 物件呼叫官方只讀查詢 `SKCenterLib_RequestAgreement`。這個功能查詢狀態，不能代替使用者簽署或啟用服務。
3. 查詢請求成功後，處理 COM 事件三秒，再嘗試一次回報連線。查詢請求成功與收到 `OnShowAgreement` 都不當作已獲交易權限。
4. 若仍為 `2018`，保留原已登入 COM owner，冷卻至少 60 秒，交由後續健康檢查再試。冷卻期間送單、撤單及行情工作都不進入執行路徑，不再呼叫 Center 登入。
5. 回報連線必須實際回傳 0，並完成新一輪回報下載。重新連線前清除舊回報，避免舊 `OnComplete` 或成交記錄被當成本輪成功。之後仍須通過原有券商餘額、庫存與正式帳本對帳，才恢復原交易流程。
6. 已建立會話的 Reply 重連亦採同一有限 fallback；其他錯誤碼沿用原有失敗處理。介面將 `2018` 說明為「證券 API 權限狀態尚未核實」，列出可能原因及重查狀態，不再暗示應開通期貨。

新增日誌只保存 API 名稱、回傳碼及狀態事件是否收到，不保存 `OnShowAgreement` 原文、帳號或憑證。

## 驗證

新增 11 項針對性測試，涵蓋暫時失敗恢復、持續失敗冷卻、同 owner 後續恢復、查詢錯誤／缺少函式／例外、非 2018 不走 fallback、新回報要求、重連路徑、禁止重複登入、復原前阻擋交易及介面說明。實機部署及完整回歸結果記錄於 `verification.json`；測試原始結果另存 `focused_regression.txt`、`full_regression.txt`。

完整離線回歸 884 項全部通過，新增針對性測試 11 項全部通過，無失敗、錯誤或略過。程式修正提交為 `90f6744`。

台灣 21:19:09，第二次定期對帳亦為 HEALTH OK，沒有新增連線錯誤。

目前為 `WAITING_RESEARCH_WINDOW`，程式心跳、版本、Windows 啟動排程、巡視迴圈、新對帳及自動交易啟用檢查通過。AI 上限 10000 元、最低保留額 5000 元、新買可用額 4080 元、單日上限 30000 元。現在盤外待命，尚未觀測新版盤中研究與正式送單。

本次實機新連線沒有觸發 `2018`，因此 fallback 的失敗後恢復路徑由隔離測試證明，不能宣稱已在實機重現並驗證同一錯誤。這次結果也不足以分辨原先是 SDK 暫時查詢失敗、上游網路問題或其他權限狀態變化；可確定的是沒有期貨交易路徑被誤觸，且本程式原有「單次失敗後永久快取」的恢復問題已修正。
