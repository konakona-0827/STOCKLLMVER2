2026-11-13；基準 `47fca25`。時間均為台灣時間 UTC+8。正式啟動、自動研究及原執行器 BUY／SELL 路徑保留，沒有改動帳戶額度、佣金或選股風控。

## 畫面同步

舊介面每 20 個 100ms tick 呼叫手動 refresh，約兩秒重讀及重繪，即使沒有新資料也顯示進度動畫。現在改為背景工作發布完成快照後通知畫面，另每五秒檢查檔案時間／大小及 SQLite WAL 作補漏；只有版本改變才讀取資料，版本相同不重查 SQLite 或全頁重繪。選取與捲動位置保留。

畫面同步不查券商或呼叫模型。券商／持倉與交易時段的研究子集行情仍約每分鐘刷新，公開行情仍約 30 秒分批；送單前按原流程再驗證。排程是目標間隔，不保證網路或 SDK 兩秒內完成。

原綠色區域顯示真正在執行的對帳、行情、官方日線、研究、下單前複核或執行器工作及秒數。閒置時不跑進度動畫，分列「畫面檢查」、「券商對帳」、「行情取得」完整日期時間，避免舊行情看起來像今日資料；失敗保留紅色提示。舊「重新整理」改為「健康檢查」，新增同名分頁。

## 券商優先與 fallback

健康檢查沿用原券商查詢及 `sync_broker_state()`：先核對券商，再依確認成交或完整新鮮庫存修正可核實的本地資料，接著重新讀取確認結果。修正收據包含原始差異、股數／歸屬修正、確認成交修正及剩餘差異，存入正式快照及健康報告。

- 曾發現並修正差異仍標「需注意」，保留本地原本不一致的證據。
- 以券商現股總數為準，未交接的新股數不直接冒充 AI 買進。保留原人工／AI 歸屬、成本來源及未結單保護。
- 未確認委託、成本不明、券商查詢不完整或資料過期時，不用本地估算硬補成交；原風控繼續阻擋未核實交易。
- 券商查詢失敗時可保留上次核對股數供畫面閱讀，但標為 `LAST_VERIFIED_NOT_CURRENT`，不恢復舊買進額度、不把舊庫存標成已驗證。這份 fallback 只供顯示，不能產生交易 payload。
- 帳本結構損壞會回報失敗，不自動刪除或重建正式交易歷史。

檢查涵蓋正式交易與歸屬帳本完整性、研究帳本、券商資料時效、庫存差異、行情、未確認委託、買進額度、FLOW 狀態、日線、近期模型紀錄、原執行器及計時檔。模型檢查只讀既有紀錄，不替代外部模型服務即時可用性測試；非交易時段明列未取盤中報價。

## BUY／SELL 計時

`execution/timing.py` 以同一 trace ID 跨過 FLOW 背景工作及原 COM owner。保留原送單與核對邏輯，沒有新增交易開關或為計時多查一次帳戶。

| 階段 | 主要紀錄 |
|---|---|
| 整輪與提案 | FLOW 開始／完成、研究完成時點、BUY／SELL 提案、當時報價時間 |
| 下單前 | 持股模型、獨立複核、券商／行情刷新 |
| 執行器排隊 | 入列、原 COM 執行緒開始、實際 queue wait ms |
| 帳戶風控 | 帳戶快照、餘額／庫存／交割查詢、BUY 逐筆最新餘額檢查 |
| SDK | 連線確認、送單開始／返回、回傳代碼與委託識別 |
| 券商核對 | 回報觀察開始／完成、確認股數與結果 |
| 帳本 | SUBMITTED 保存開始／完成、確認成交或狀態回寫耗時 |

時間戳為含時區的台灣時間；毫秒偏移與階段耗時來自單調時鐘。巢狀階段會重疊，不能直接加總。紀錄含報價到 SDK 送單的年齡、提案到 SDK 的時間與可取得時的研究到送單時間，便於之後檢討時間耗損。記錄功能不提供保證成交或延遲改善的績效結論。

「執行耗時」分頁顯示最新一輪，原執行報告有 `execution_timing`、正式委託明細有 `timing_ref`；有買賣提案時歷史存於**正式資料根目錄**的 `data/execution/timing/<trace_id>.jsonl`，不是另一套帳戶。API／檔案寫入失敗也留在結果；計時寫檔失敗不重送或改變委託，原 SEND_PENDING／券商核對仍是交易安全依據。

只用可核實的券商成交列計算成交均價及相對最後觀測買賣價的滑價；不拿限價冒充成交價。缺少識別、價格或完整確認股數時為未知。SDK 開始但沒有回傳的紀錄也不能當成未送單，仍須由原核對機制處理。

```powershell
python -m operations.review_execution_timing --date 2026-11-13 --output local_data/execution_timing_review.json
```

## 交易電腦事故分支檢討

已讀取遠端 `codex/opportunity-flow-incident-20261113`，事故保存提交為 `6978ee08ea7c551ab0bf8b01ff47452fb5c44e85`。[事故說明及原始證據](https://github.com/konakona-0827/STOCKLLMVER2/tree/6978ee08ea7c551ab0bf8b01ff47452fb5c44e85/reports/opportunity_flow_incident_20261113) 記錄：實際程式基準為 `d740a35`，UI 顯示 `ImportError: cannot import name 'pending_exit' from 'position_manager'`；當時掃描輪數、模型呼叫、委託交接均為 0。券商在 08:30:12 已完成一次對帳，但錯誤發生秒數未記錄。

原因是 `LegacyRuntime.candidates()` 從錯誤模組匯入 `pending_exit`，真正定義在 `execution.exit_cancel`。此錯誤也存在 `a57635f`，但已在目前分支的祖先 `d7e656f` 修正，這次比對沒有重新引入。`test_real_runtime_candidate_context_imports_pending_exit_without_broker_access` 直接執行真實候選整理，防止只用替身測過研究流程卻漏掉匯入錯誤。事故證據顯示程式於研究前中止，不能把這次 0 機會歸因於選股結論。

事故保存提交另包含舊簡易 `ControlPanel` 的停止／重啟介面修改。正式 `launch()` 已轉向完整 `FlowDashboard`；目前 `FlowController.start()` 在前一執行緒未結束時拒絕重啟，`runtime_action()` 在啟停過渡期拒絕另開券商，`LiveCoordinator.close()` 也已持鎖關閉原 runtime，保護目的已涵蓋。保留現行完整 UI，不直接合併舊介面與事故快照覆蓋新版。

08:30 公開行情批次另外記錄 40 筆錯誤；保存資料沒有每筆錯誤類型，不能斷定其個別原因，也不能據此認定盤中行情已驗證。現有流程仍區分公開參考價與券商可執行報價，資料失敗不得放行買賣。
